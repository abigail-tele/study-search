# How It Works

Plain-English tour of every module. Each section should be 3 to 5 sentences that a team member can explain to a judge.

## config.py

Central settings for the whole project. Every path, threshold, k value, and UI string lives in `backend/config.py`, so tuning happens in one place and every "magic number" is visible at once. Paths are built from the project root, so the app runs the same way on any computer. Search settings (how many candidates each method returns, the RRF constant, and the thresholds for detecting cancer types) and PDQ and model settings each have their own section. Other modules import these names instead of hard-coding values.

## app.py

The web server only reads files already on disk (SQLite, the FAISS index and the local MiniLM model in `models/`); it never calls ClinicalTrials.gov or Hugging Face while a person is waiting. When it starts, it loads the model and index once so the first visitor is fast and any missing file shows up immediately instead of mid-search. Hugging Face offline mode is switched on in code and in `run_api.ps1` as a second safety lock. Search text and ZIP codes are scrubbed from logs. Run `python -m pipeline.fetch_models` once before the first start.

## embedding.py

This small module is the single place that turns text into 384 numbers with all-MiniLM-L6-v2, so trials (offline) and questions (live) share one vector space. It loads the model only from the local `models/all-MiniLM-L6-v2` folder and raises a clear error if it is missing, rather than quietly downloading it during a request.

## db.py

db.py defines our database, a single SQLite file that holds every trial, the cancer types it was matched to, its hospital sites with map coordinates, a keyword-search index, and the saved plain-language summaries. SQLite needs no server, so the website can simply read the file. A helper turns ages like "6 Months" or "18 Years" into one number of years so we can filter by age later. When a trial is saved again, its old row is replaced so the database always matches the newest version from ClinicalTrials.gov.

## taxonomy.py

This file holds the list of cancer types (breast, lung, leukemia and so on) and broad phrases like "blood cancer" that stand for several types at once. Its main job is `detect_cancer_types`, which reads what a patient typed and decides which cancer type they mean. It first looks for exact wording (every lay or clinical name as whole words, plus an organ word near "cancer", so "breast and lung cancer" finds breast and both lung types) and adds broad phrases like "blood cancer"; a broad phrase is skipped when the patient already named something more specific ("chronic lymphocytic leukemia" is only that one type). Only if nothing matched does it try close spellings ("brest", "leukemea") and, last, a meaning comparison using the same small MiniLM model as search, which also requires a cancer word in the query so "stomach ache" is never read as stomach cancer. Very short names like AML or CLL only count as whole words, and the bare word "all" never counts, so "small", "camel" or "all of my family" never trigger a leukemia. If nothing matches, the question is not about cancer and the app shows cancer buttons instead of searching, which is how we keep to the cancer-only rule. This function was written by Claude Code at the team's request, so team members must review it and be able to explain each step.

## search.py

Search first narrows the database to trials tagged with every cancer type found (a query naming two cancers keeps trials of both), and to the status, age and distance the patient chose, so every ranked result is usable. Inside that group it makes two ranked lists: one from keyword matching (SQLite FTS5) and one from meaning matching (FAISS over MiniLM vectors, which finds trials that say the same thing in different words). Reciprocal rank fusion (`reciprocal_rank_fusion`, written by Claude Code at the team's request, team to review) then merges the two lists by giving each trial 1/(60 + position) points from each list, so trials that both methods like rise to the top; keyword scores and meaning scores are on different scales, but positions can be compared. Ties are broken by NCT ID so results never shuffle between runs. Finally the top 10 become cards, each with a citation built only from stored ClinicalTrials.gov fields and, if a ZIP was given, the distance to the nearest site. Nothing here calls the internet, and the query and ZIP are never saved or logged.

## summarize.py

summarize.py turns a trial's brief summary and eligibility text into plain language in four steps. First, plan_pieces splits the eligibility text into "can join" and "cannot join" lists and cuts long text into whole-sentence pieces that fit the small model's input limit. Next, the fine-tuned flan-t5 model rewrites each piece, and judge_chunks runs faithfulness_check on every rewrite: each number, age, unit, dose, gene or marker, stage term and drug name in the rewrite must also appear in the source, and flipped comparisons or negations are rejected. Sentence-level guards from backend/support.py then drop any rewritten sentence that drifts from the source, and a piece that fails the check is replaced by the original wording with hard words explained from the NCI-based glossary. assemble_summary sets `fallback_used` if any piece fell back and `faithful` only when everything shown is checked model text; faithfulness_check was written by Claude Code at the team's request, is marked AI-written, and must be reviewed and explained by the team.

## support.py

support.py holds the automatic safety nets that run after the model rewrites a chunk, on top of the number-and-drug faithfulness check (AI-written at the team's request). The support check compares each rewritten sentence with the source using sentence embeddings (MiniLM) and also requires most of its words to come from the source or the NCI glossary, so a fluent but invented sentence like "Women over 18 are more likely to get breast cancer" is dropped. Further filters drop generic textbook openers, "X is a type of X" sentences, risk words the trial never used ("likely", "cure"), and definitions the source did not give. The direction check looks for rules turned into their opposite: a number whose bound flips ("at least 18" becoming "under 18", ">= 2" becoming "<= 2"), and a statement whose negation flips ("no prior chemotherapy" becoming "prior chemotherapy", "excluded" becoming "included"). It does this by comparing short clauses that share most of their topic words; when the wording differs too much to compare, it stays quiet instead of guessing, so it is a cheap tripwire rather than a proof. All thresholds and word lists live in config.py.

## readability.py

readability.py estimates how hard a text is to read, using the Flesch-Kincaid grade formula: longer sentences and longer words raise the grade. We wrote the short formula ourselves instead of adding a library, with a simple vowel-group syllable counter, which is accurate enough to compare the original text with our rewrite but not to publish as an exact grade. summarize.py stores a "before" and an "after" grade with every summary so the app can show that the plain-language version is easier to read.

## geo.py

geo.py answers "how far is this trial from me?". It looks up the center point of a ZIP code in a public-domain US Census table, then uses the haversine formula (straight-line distance over the curved Earth) to measure miles to each trial site. It picks the nearest site and reports its city, state, and distance. These are plain functions that keep nothing, so a visitor's ZIP code is never stored.

## zip_centroids.py

zip_centroids.py builds `data/zip_centroids.csv`, the table geo.py uses to turn a ZIP code into a map point. It downloads the US Census Bureau's public-domain ZIP-area (ZCTA) gazetteer once, keeps only the ZIP, latitude and longitude columns, and writes a small CSV. It runs by hand, not while the website is running, so no visitor ever triggers a download and no ZIP code is stored.

## indexer.py

indexer.py is the offline script that fills the database; the live website never talks to ClinicalTrials.gov. For each cancer type it sends that type's search phrase to the ClinicalTrials.gov API, asks only for the fields we need, and walks through the results page by page, pausing between pages and retrying with longer waits if the server is busy. We keep only open or ongoing trials, and a trial that matches two cancer types is stored once with two tags. A later run can fetch just trials changed since a given date to keep the data fresh; that run asks for trials of every status, so a trial that has since closed is noticed and deleted instead of staying "Recruiting" forever.

ClinicalTrials.gov's search is loose ("small cell" also finds "non-small cell", and "cervical" also finds the neck), so we do not trust its match. Before saving, the indexer re-reads each trial's conditions, keywords and titles and tags it with a cancer type only if one of that type's own words appears as a whole word. Each type can list `exclude_patterns` in `data/cancer_types.json` (for example "non-small cell" for small cell lung cancer, "cervical spine" for cervical cancer) that are blanked out first. A trial must also pass a general cancer check (words like cancer, tumor, leukemia, lymphoma, or acronyms like NSCLC and AML); anything else, such as PCOS or burn studies that slipped in, is never stored. If a trial is clearly cancer but names no type, it keeps the type of the search that found it, unless an exclusion pattern fired. The command `python -m pipeline.indexer --retag` applies these same rules to the existing database without downloading anything, and writes every removed trial to `data/retag_dropped.csv` so a person can spot-check it.

## embed.py

This offline script turns every trial into a list of 384 numbers that captures its meaning, using the small open model all-MiniLM-L6-v2. The text we feed it is the title, conditions, keywords and brief summary, because those say what the trial is about while the long eligibility list would add noise. The vectors go into a FAISS index (a fast lookup file) and a companion file that says which trial each row belongs to; the script checks the two counts match. Run it again whenever the indexer adds trials: `python -m pipeline.embed`.

## pdq_pairs.py

The National Cancer Institute publishes many cancer summaries twice: once for doctors and once, in simpler words, for patients, and both are public domain. This script downloads both versions of each page (treatment, screening, prevention and supportive care, listed in `data/pdq_pages.json`), cuts them into sections, and pairs up sections whose headings match (for example "Treatment of Stage III Colon Cancer" on both pages). Inside each matched section it turns every paragraph into a list of numbers that captures its meaning and pairs each patient paragraph with the doctor text that means the most similar thing; the doctor side may be one to three paragraphs joined, because one patient paragraph often condenses several. A second pass then looks across the whole page for leftover patient paragraphs, using a stricter similarity bar because the headings no longer back the match up. Weak matches, copied text, answers much longer than the original, and pairs where the patient text mentions a number or stage that the doctor text never mentions are thrown away (so the model is not taught to invent facts), and patient sentences that just point elsewhere ("see the booklet...") are cut out first. Finally, whole organ families (colon with rectal, the two lung cancers, Hodgkin with non-Hodgkin lymphoma, adult with child versions) are assigned together to the training, validation, or test group, and any validation or test example whose answer is almost a copy of a training answer is removed, so the model is never tested on text it effectively studied. The result is the file of before-and-after examples used to teach our small model to simplify medical text.

## train.py

This script teaches a small existing language model (Google's flan-t5-base) to do one job: take a paragraph written for doctors or a trial and rewrite it in plainer words. The production model (called G in `docs/EVAL.md`) learns from two kinds of before-and-after pairs: cleaned National Cancer Institute pairs from `pdq_pairs.py`/`clean_pairs.py` and in-domain ClinicalTrials.gov pairs from `ctgov_pairs.py` (a random 2,000 of them, so the NCI pairs are not drowned out). Only pairs whose similarity score is at least 0.70 are kept, so it is not taught to say things the original never said. Training repeats one loop: show the model a batch of source paragraphs, measure how far its rewrite is from the real plain version (the "loss"), and nudge its numbers to shrink that error. After each full pass it checks the loss on separate validation pairs, saves the best version so far, and stops early when the model stops improving, which prevents memorising the training pairs. The test pairs are never touched, so the final evaluation stays fair.

## batch_summarize.py

This offline script prepares a plain-language summary for every RECRUITING and NOT_YET_RECRUITING trial ahead of time, so patients get it instantly. It works in two stages. `generate` runs on the RTX 5090 graphics card: it cuts each trial into the same pieces the live site uses, has the fine-tuned model rewrite them in batches of 128 (longest first), and saves the raw rewrites in the `model_outputs` table; it can be stopped and restarted because finished trials are skipped. `check` runs on the ordinary processor: it sends every saved rewrite through faithfulness_check and the guards using judge_chunks from summarize.py (the same code the live site uses), swaps in glossary-explained original wording wherever a rewrite fails, and writes the `summaries` rows the website reads. The first real run (with the older clean-sent model) covered 20,432 trials and 413,998 pieces: 255,460 pieces (61.7%) were shown as model text and the rest as original wording, and fallback_used was true for 20,107 of the trials. Those counts are from the old model; the production model is now G and the summaries are regenerated, see the "Production summaries" section of `docs/EVAL.md` for current numbers. Results are written to data/batch_summary_stats.json, and because the slow generation step is saved separately, re-running `check` after faithfulness_check changes refreshes every summary without regenerating anything.

## evaluate.py

This script measures the search side of the app and writes the numbers into `docs/EVAL.md` and `results/eval_retrieval.csv`. For each of the 25 everyday-language test questions it runs the keyword search (word matching) and the meaning search (embeddings) separately, inside the trials tagged with the right cancer, and checks the top 10 for the expected cancer type. That is only a stand-in score; the real hit@5, MRR and recall@10 are computed automatically once humans list the correct trials in `data/test_queries.json`. It also times each search path (with and without a ZIP filter) and copies in the summary-pipeline counts and the model-comparison numbers that other scripts already produced. Parts that depend on the team-written functions (merging the two rankings, spotting off-topic questions) say "pending" until those exist, then fill in on the next run. It never touches the held-out PDQ test pairs.

## make_ship_db.py

The full database is big because it holds things only the offline scripts need. This script copies it into `data/trials_ship.db` using SQLite's own backup feature on a read-only connection, so it is safe even while another script is writing. It then deletes the tables and columns the live website never reads (long descriptions, cache tables) and compacts the file. Setting the environment variable `STUDY_SEARCH_DB` to that file makes the website use the slim copy.

## frontend

The frontend is one plain HTML page with CSS and JavaScript, with no build step and no outside libraries. It reads data through `api.js`, which has one flag (`USE_MOCK`) that switches between fake files in `frontend/mock/` and the real `/api/...` endpoints. `app.js` draws the search form (with the collapsible "About you" section), result cards with match badges, and the study panel (at a glance, what they're looking for, who can't join), and the eligibility lists show the original criterion wording (with plain definitions) by default, because a spot-check found some model-written bullets that said things the source did not; a labeled toggle switches to the checked simplified wording for that page view only. It only inserts API text with `textContent` so data can never run as code. The query and filters are kept in the page address (never the ZIP code), and nothing is saved in cookies or local storage. Colors always come with words (for example the status badge), text is at least 16px, and every control works with a keyboard.

## data/umbrella_terms.json (note for type detection)

Broad phrases such as "lung cancer", "skin cancer" or "blood cancer" are not single cancer types, so they live in `data/umbrella_terms.json` (phrase to list of type ids) instead of any one type's lay terms. Detection must show all the listed types for these, and must never match the bare word "all" (the lay term "all leukemia" only counts as that whole phrase).

## baselines.py

baselines.py answers "is our fine-tuned model actually better than simple alternatives?" It runs the same examples through easy comparisons (copying the source unchanged, the untrained flan-t5 with a simple prompt, the untrained model shown three examples) and through each of our trained checkpoints. Every output gets scored for how close it is to the NCI patient wording (ROUGE and word-overlap precision, recall and F1) and for key terms like numbers, drugs and stages, where low precision means the model invented facts. The scores are written to a results table and error-analysis files so we can show judges the evidence.

## clean_pairs.py

The first models we trained picked up textbook habits such as "X is a disease in which..." and wrote them even when a trial never said so. clean_pairs.py goes through every training answer sentence by sentence and deletes the ones that are generic openers or that the source text does not support, using the same support check the live app uses (with looser limits, since patient and doctor wording differ). If too little of an answer is left the whole pair is dropped, and duplicates are removed again. The original files are never overwritten, so the cleaning can be re-run or undone.

## compare_checkpoints.py

Each training run splits its own validation data, so their loss numbers can't be compared fairly. This script freezes one fixed set of 125 validation pairs and scores every checkpoint on it the same way: loss, ROUGE-L against the NCI patient text, reading grade level (lower is easier), and the share of outputs whose numbers all appear in the source. That lets us pick the best checkpoint by facts instead of by feel. It never touches the test split, which stays reserved for the final evaluation.

## match.py and overview.py ("About you")

A person can optionally type their age, sex and a few conditions (for example "HER2 positive, stage 3, had chemotherapy"). `match.py` cuts the text into short terms and compares them with one trial at a time. Age and sex are checked against the trial's stored limits. Each term is looked for in the trial's inclusion and exclusion rules as whole words (with spelling variants such as "stage III" = "stage 3" and a short synonym list), and, if no words match, by meaning using the same MiniLM model as search (terms with numbers must match exactly). A match in a requirement is shown with a check mark, unless the rule is negated ("no prior chemotherapy"), which is flagged as a possible conflict; a match in an exclusion is flagged to check. The result is one of "Possible match", "Check with study team" or "Likely not a match", always followed by "the study team decides who can join"; we never say someone is eligible. Nothing typed is stored or logged. `overview.py` fills a fixed sentence template ("A Phase 2 study, now recruiting, for people ages 18 and older...") from stored fields only, so the model never writes the key facts.

## ctgov_pairs.py

Most of our training text comes from National Cancer Institute pages, but clinical trials are written in their own style, so this script builds extra training pairs from ClinicalTrials.gov itself. Many trials have a technical detailed description and a shorter brief summary that restates parts of it, so the script matches each brief-summary sentence (or a two-sentence window) to the best one to three detailed-description sentences, using the same MiniLM sentence model that search uses. It keeps a pair only if the plain version is easier to read, is not longer than the original, adds no new number, stage, drug or gene, and has no boilerplate, which stops the model from being taught to invent facts. Trials in our fixed evaluation set are excluded, and the train/validation split is decided by a hash of the NCT number so all pairs from one trial land on the same side. It reads the database read-only and writes the pairs and their statistics under `data/`.

## train_lora.py

Our first model, flan-t5-base, is a small encoder-decoder; this script instead fine-tunes Qwen2.5-1.5B-Instruct, a small chat model, using LoRA. LoRA trains only small adapter matrices added to the model rather than all 1.5 billion weights, so training fits and runs quickly on one GPU. Each example is wrapped in the same chat prompt that generation uses, and the loss is computed only on the plain-language answer, so the model learns to write answers rather than to copy the source. Recipe J uses our default settings (rank 16, learning rate 1e-4, early stopping on validation loss); recipe J2 uses rank 64 with alpha 16, a learning rate of 2e-4, and a short sweep over one and three epochs, with settings adapted from a team member's friend's fine-tuning script and the code written fresh. The winner is chosen on validation loss only, never on the test split, and the adapter is merged into the base weights at the end so the saved folder is an ordinary model that `baselines.py` can load.
